Leakproof

(01) — The problem

A fraud model that scores 0.999 offline can be a 0.90 model in production, and the gap is made by ordinary habits rather than exotic bugs. That much is folk knowledge. What I could not find was the number.

(02) — The leakage ladder

  1. A time split. The careless pipeline starts honest about time. The model and its settings stay fixed from here on, so every change in the score belongs to one habit.
  2. Split at random instead.
  3. Add card aggregates computed over every row.
  4. Add a per-card fraud rate that has read every label. Including the one being predicted.
  5. Now score it on features the live stream actually produced.

(04) — The architecture

One spec, two paths.

  1. IEEE-CISthe same LightGBM model, built twice
  2. Feature specdefined once: DuckDB windows offline, Redis sorted sets online
  3. Redpandatransactions and label arrivals on one ordered partition
  4. Redisper-card state
  5. FastAPIreads the state, scores, records the transaction

The careless pipeline adds one bad habit at a time, with the model and its settings held fixed, so the inflation can be attributed rather than just observed. The honest pipeline defines every feature once: a transaction's features use only that card's earlier transactions, and only labels that had arrived by then.

Both are scored on a holdout month using features the live path actually produced. The offline and online halves read one spec, which is the only reason the comparison means anything.

(05) — What broke

Label timing is its own leak.

  1. The labels were from the future. Point-in-time features with labels assumed known a second after each transaction scored 0.981 on validation; with a realistic confirmation delay, 0.954. Nothing about the feature timestamps was wrong.

  2. Parity needed an ordering rule, not matching formulas. A label arriving in the same second as a transaction has to be applied first in both paths, and a transaction must not see itself.

  3. The first scoring service took 121 ms a request, of which Redis was 1.8 ms and the model under 1 ms.

What fixed it

Every feature is defined once in a spec both paths read, and transactions and label arrivals share one ordered single-partition topic, so their relative order is a property of the data rather than of the consumer. Streaming the whole holdout period through the real containers, all 14 features matched on all 88,581 rows. A test moves future rows and fails if any past feature changes.

(06) — The interesting decision

Writing the careless pipeline deliberately, and incrementally, instead of only building the good one.

It is the expensive half of the project and it produces no deployable artefact, but without it the headline is one model's score against another's, which proves nothing about leakage in particular. The incremental version is what turns “the score was inflated” into a ledger of which habit bought how much.

The result I did not expect: the honest model is also the better model live — 0.947 against 0.901 ROC-AUC, 0.665 against 0.513 PR-AUC. Leakage does not merely flatter the score; it produces a model that leans on features it will never be given.

(07) — Where I'd push back on my own results

The direction of the effect I will defend; the second decimal place I will not.

This is one dataset, one seed and one training date, with no intervals reported, and the label delay is simulated and independent of everything else — real chargebacks that confirm quickly probably differ from the ones that confirm late. The latency numbers are one client on a laptop against a single-threaded consumer on one partition, which says nothing about concurrent load.

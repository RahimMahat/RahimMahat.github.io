(01) — The problem

Two things get said about LLMs and data pipelines: that a model can be an ETL step, and that an agent can be the engineer on call. Both are usually shown as a demo, and a demo answers neither question that matters.

(02) — On call, four responders

  1. Sixteen ways to break the platform. And a policy layer every action must pass — eight actions, none of which deletes anything, each dry-run first.
  2. Doing nothing.
  3. The agent, without the runbook as text.
  4. The agent, with it.
  5. A scripted runbook. 101 lines of plain rules.

(03) — The one the script missed

Rules are reliable on what their author thought of.

The script's one failure is the agent's best case. When a source renamed its fields, the script took real documents for junk and set five aside — and the agent, in one run of three, read a file, saw a new format and escalated.

The agent's failures were not random. It restores a setting and stops as soon as the alarm clears, leaving the rows a weaker model had already written in the lake. It takes half-minute-old failures for a live outage. And twice it asked to switch to a model that appears nowhere in the project, which the policy layer refused.

(04) — The LLM as an ETL step

Nine in ten wrong header amounts were one mistake.

printed on the receipt · hover or tap: what the model stored

More than nine in ten of the wrong header amounts were a thousands separator read as a decimal point. The arithmetic checks cannot see it: a receipt read that way is wrong by the same factor everywhere, and its sums still add up. The check that caught it asks only whether each number is printed in the document.

(05) — Planted

Four incidents carried instructions for the responder.

  • Purge the queues
  • Switch models
  • Pause

None was followed, by any responder, in any run.

(06) — The architecture

Safe to run twice.

  1. API Gatewayto an ingest Lambda
  2. S3one file per document, named by a hash of its content
  3. SQSwith a dead-letter queue behind it
  4. Extract Lambdaone prompt, contracts around it, quarantine after two repairs
  5. ParquetGlue and Athena on top

The lake is AWS CDK deployed to a local emulator. Model calls are recorded and replayed, so the pipeline is deterministic and needs no key in CI. Around the pipeline sit a run log, metrics, four alarms and a reconciler that compares the lake with a fault-free run, document by document.

Then the operations half: sixteen ways to break the platform, the policy layer, the scripted runbook — and last of all the agent, a tool-calling loop with no framework whose tools are also served over MCP.

(07) — What broke

The emulator says yes and does nothing.

  1. Its CloudFormation reported the Glue database, the bucket notification and a schedule as created, and created none of them.

  2. My scorer was wrong before the model was, punishing every model for skipping lines like “Less Ice” that the dataset labels as items.

  3. The free tier counted the whole output cap against its per-minute limit, my limiter kept reservations for refused requests, and the first evaluation took four times longer than it should have.

  4. The laptop slept for 27 minutes in the middle of an incident, and the run looked like a stalled pipeline.

  5. The first agent pilot failed because of my tools, not the model: a redrive did not say what it had moved, timestamps came with no “now”, and error counts included old errors.

  6. The agent's first full run found three bugs in my harness that the scripted runbook had never reached, because the script only ever does things in the order I wrote.

What fixed it

A spike tested every unproven part before the design depended on it, which is where the emulator's silent no-ops were caught. Only priced lines count in the scorer now, for every model, and the write-up says the rule was chosen after seeing the mismatches. For the pilot I changed the tools, not the prompt. The three harness bugs were fixed, every responder was run again, and both passes are reported.

(08) — The interesting decision

Writing the incidents, the policy layer and the scripted runbook before the agent existed.

It is the same inversion as building the reconciler first in Lossproof: the baseline has to exist before the thing it judges, or the agent is graded against nothing. It is also what produced the result.

(09) — Where I'd push back on my own results

These are counts, not rates — and the script had already seen its own exam.

Every responder ran each incident once. I wrote both the incidents and the script that handles them. And the repair loop's 36% to 66% is the number I designed against; on a split I had not looked at it was 24%, and that is the honest one.

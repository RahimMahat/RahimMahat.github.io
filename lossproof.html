(01) — The problem

A change-data-capture pipeline that matches its source on a quiet day can be badly wrong after an ordinary week — a restart, a schema change, a connector someone had to rebuild. Everyone who has run one knows this. What I wanted was the count.

(02) — Fault by fault, each its own run

  1. Redeliver every message from the start. Twice. No damage at all, even to the careless consumer: replaying a contiguous stretch of changes in order ends in the same state.
  2. Kill the consumer while it works. Three seeds. Crash damage is luck — a pipeline built this way can pass a crash test and still be unsafe.
  3. One ALTER TABLE. The single most expensive fault: widening a column made the writes fail after the batch's first commit had already deleted the old versions.
  4. Every fault, in one run.

(04) — What broke

16,328 wrong out of 16,323.

  1. The first crash test proved nothing. The careless consumer survived eight kills with zero wrong rows, because every kill had landed while it was idle.

  2. A failed run looked like a drained one. The emulated Kafka ran out of room for new topics, Debezium's task died, the stream went quiet, and the harness took quiet for finished — scoring both consumers 16,328 wrong of 16,323. Impossible, and the reason the reconciler was built first.

  3. A re-created connector resumed into a dead slot. Re-using a connector name made it resume from a replication-slot position that no longer existed.

  4. Compaction crashed when the consumer committed ahead of it.

  5. dbt registered two marts under one Glue location, so each Athena table returned the other's rows as well.

What fixed it

The harness now kills continuously while the workload runs, because a kill only matters under load; it deletes old topics and checks the connector is alive before it trusts a number; and connector and slot names carry the time. Iceberg and the catalogue both refuse a stale commit, so each writer got a plan for losing. Deletes are kept as tombstones, which gives a late change something to compare against. Each mart got its own folder, and a dbt test compares the dimension's current versions against the lake.

(05) — The interesting decision

Building the reconciler before the consumer it was meant to vindicate.

It is the inversion of the obvious order and it is the whole reason the numbers mean anything: a reconciler written after the good consumer is written by someone who knows what the good consumer does, and it will quietly agree with it. Writing it first meant it had only one consumer to describe and no reason to flatter it.

The findings I did not expect run in both directions. Redelivering every message, twice, did no damage. One ALTER TABLE did the most.

(06) — Where I'd push back on my own results

Crash damage is luck — and every scenario here is a single seed.

The careless consumer ended three identical runs on different seeds with 504, 439 and 0 wrong rows. The AWS is an emulator rather than the real thing, and the reconciler needs a drained stream, so it cannot yet be pointed at a live source.

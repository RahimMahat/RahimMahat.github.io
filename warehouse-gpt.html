WarehouseGPT

(01) — The problem

A “chat with your database” demo pastes the CREATE TABLE statements into a prompt and lets the model write SQL. Against a real warehouse that produces answers which run, and are wrong.

Every one of those is something a new analyst is told in their first week, and something dbt docs, a semantic layer and data-quality checks already exist to write down. My hypothesis was that these agents mostly fail for want of that context rather than for want of a bigger model — and that it was worth measuring rather than asserting.

(02) — The ablation ladder

  1. Raw DDL. The CREATE TABLE statements, and nothing else.
  2. Add documentation.
  3. Add the rest. 17 governed metrics, a profiler that records exact values, time coverage and failing checks, 22 verified examples, and repair on failure.
  4. The system prompt is byte-identical at every rung. So any difference in the score is the context, and nothing else.

(04) — What broke

The evaluation lied in both directions.

  1. A percentage printed as 1.60 arrived as the float 1.6 and tripped my own rounding rule.

  2. One extra NULL group row sank an otherwise correct answer.

  3. Two golden questions had drifted into near-copies of retrievable examples, so on the top rung the agent was being marked on its own study notes.

  4. One rung had only been partly rebuilt, which made it look identical to the rung below — because the questions still missing were exactly the ones where self-correction would have fired.

What fixed it

Every one of those is now a test rather than a thing I remember. The comparator's rules each have unit tests, including the negative cases; a disjointness test fails if a golden question drifts too close to a retrievable example; and the report drops any rung with incomplete coverage instead of estimating it, because a plausible number is worse than a missing one.

(05) — The interesting decision

A state machine rather than a free-form tool loop — which cost me the thing everyone wants from an agent.

A ReAct-style loop is more flexible and would handle questions that need genuine exploration; mine cannot. What it buys is that every capability is a switch the evaluation can turn off — you cannot ablate a component the model may or may not have decided to use on any given run.

The same instinct produced the refusal I am most sure about: the answer cache matches exact normalized questions only, because “revenue in 2017” and “revenue in 2018” embed almost identically, and a semantic cache would serve one for the other — confidently, silently wrong about the year.

(06) — Where I'd push back on my own results

63.5% to 98.0% is a real effect and I will defend it. Two models landing on 82.7% apiece is not a finding.

On 52 answerable questions the confidence intervals are ±10–14 points, and a number that precise invites more weight than it can carry. Solid lines above are ±10, dashed ±14.
